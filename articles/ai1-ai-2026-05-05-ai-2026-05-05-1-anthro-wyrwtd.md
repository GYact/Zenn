# Claude Opus 4.7 移行ガイド：breaking changes を整理して本番コードを安全にアップグレードする

## はじめに

Anthropic が 2026年4月16日に Claude Opus 4.7 をリリースし、公式の表看板としては「価格据え置き」と謳っている。ところが実際に Opus 4.6 のコードをそのまま動かすと、すぐに `400 Bad Request` が飛んでくる。「明日デプロイしたら壊れる」という状況で自分も実際に Claude Code のセットアップや API エージェントループを移行する羽目になった。新モデルはリアルな coding work では明らかに速く、スクリーンショットの読み取り精度も段違いだ。ただしこれが最初の Claude リリースで、アップグレードに実コード変更が必要なケースである。

本記事では breaking changes の全量を整理し、コピペで使える移行コードと、見落としがちなコスト罠まで踏み込んでカバーする。

---

## 背景：何が変わったのか

Claude Opus 4.7 は現時点で GA の中では最高性能のモデルとして位置づけられており、高度な software engineering において Opus 4.6 を大きく上回っている。特に難易度の高いタスクで伸びが顕著で、ユーザーからは「以前なら目を離せなかった困難なコーディング作業を、自信を持って丸投げできる」という声が上がっている。

ただし、その恩恵を受けるためには **API レベルでの後方互換性のない変更** を処理しなければならない。

### 4 つの breaking changes

Messages API には Claude Opus 4.7 における 4 つの breaking changes がある。Extended thinking のbudget が廃止されたため `budget_tokens` は 400 エラーを返す。`temperature`・`top_p`・`top_k` のような sampling パラメータもデフォルト以外の値を渡すと 400 になる。thinking content はデフォルトでレスポンスから省略されるようになり、adaptive thinking 自体もデフォルトではオフになった。さらにトークナイザーが新しくなり、同じテキストが Opus 4.6 比で最大 35% 多いトークンとして数えられる。

---

## 実装：移行チェックリスト

### Step 1：サンプリングパラメータを削除する

もっとも単純だが、見落としやすいのがここだ。`temperature=0` を使って出力を安定させていたコードは全滅する。

```python
# ❌ Opus 4.6 まで動いていたコード（Opus 4.7 では 400）
response = client.messages.create(
    model="claude-opus-4-7",
    temperature=0,        # 400: sampling params removed
    top_p=0.95,           # 400: sampling params removed
    max_tokens=8192,
    messages=[{"role": "user", "content": "..."}],
)
```

```python
# ✅ Opus 4.7 向け
response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=8192,
    messages=[{"role": "user", "content": "..."}],
)
```

なお、`temperature=0` を使っていた場合でも、それが Anthropic API で同一出力を保証していたわけではもともとない点に注意。

---

### Step 2：Extended thinking → Adaptive thinking への置き換え

これが最大の変更点だ。

旧来の Claude では「事前にどれだけ難しい質問かを自分で予測して `budget_tokens` を設定する」という奇妙な作業が必要だった。`budget_tokens: 32000` を指定して、コードベースのリファクタには十分でもメール要約には過剰でないことを願うような運用だ。Opus 4.7 はそのパターンを廃止した。Adaptive thinking が唯一の thinking-on モードとなり、旧 `budget_tokens` パラメータは 400 エラーを返す。代わりにモデルがプロンプトを見て難易度を推定し、難しい問題には多く、単純な問題には少ないトークンを動的に割り当てる。

```python
# ❌ Opus 4.6 の extended thinking
response = client.messages.create(
    model="claude-opus-4-6",
    max_tokens=64000,
    thinking={"type": "enabled", "budget_tokens": 32000},
    messages=[{"role": "user", "content": "..."}],
)

# ✅ Opus 4.7 の adaptive thinking
response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=64000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},  # "low" | "medium" | "high" | "xhigh" | "max"
    messages=[{"role": "user", "content": "..."}],
)
```

Adaptive thinking はリクエストごとの複雑さに応じてモデルが動的に extended thinking の使用量を決定する。

#### effort レベルの選び方

Opus 4.7 の effort は `low`・`medium`・`high`・`xhigh`・`max` の 5 段階。Claude Code はすべてのプランで `xhigh` がデフォルトになっている。これが intelligence とトークン消費のバランスを取る最大のレバーだ。Hex の CTO によれば「`low` effort の Opus 4.7 はほぼ `medium` effort の Opus 4.6 と同等」であり、すべてを `xhigh` にするのは無駄が多い。

| effort | 用途 |
|--------|------|
| `low` | 分類・抽出・フォーマット変換など単純タスク |
| `medium` | 短い要約・FAQ応答 |
| `high` | 複数ステップの推論・コードレビュー |
| `xhigh` | エージェント型コーディング・複雑なデバッグ |
| `max` | 最高精度が求められる長時間タスク |

---

### Step 3：thinking.display のデフォルト変更に注意

Opus 4.7 から、thinking content はデフォルトでレスポンスから省略されるようになった。thinking blocks はレスポンスストリームに登場するが、明示的にオプトインしない限り `thinking` フィールドは空になる。これはサイレント変更でエラーは発生しないが、レスポンスのレイテンシはわずかに改善される。

推論内容をユーザーにストリーミング表示していた場合、対応しないと長い無音状態が発生するので注意。

```python
# ✅ reasoning を UI に表示したい場合は display を明示する
response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=64000,
    thinking={"type": "adaptive", "display": "summarized"},
    output_config={"effort": "xhigh"},
    messages=[{"role": "user", "content": "..."}],
)
```

---

### Step 4：Task Budget でエージェントループのコストを制御する

Task budget は Opus 4.7 の最も興味深いランタイム機能の一つだ。エージェントの full loop（thinking・tool calls・最終出力を含む）のトークン予算を開発者が定義でき、モデルはカウントダウンを見ながら残りのタスクに対してどれだけ検索・ツール使用・合成をすべきかを判断する。これは `max_tokens` とは異なる。`max_tokens` はモデルが見えない hard ceiling であり、計画上の判断には影響しない。

```python
import anthropic

client = anthropic.Anthropic()

response = client.beta.messages.create(
    model="claude-opus-4-7",
    max_tokens=128000,
    output_config={
        "effort": "high",
        "task_budget": {"type": "tokens", "total": 64000},  # 最小 20,000
    },
    messages=[
        {"role": "user", "content": "このコードベースをレビューして、リファクタ方針を提案してください。"}
    ],
    betas=["task-budgets-2026-03-13"],
)
```

Task budget はあくまで advisory（勧告的）であり、強制ではない。minimum total は 20,000 トークンであることも念頭に置いておこう。

## コスト罠：「価格据え置き」の隠れた罠

「価格据え置き」のリリースノートでそこで読むのをやめると、大規模に Opus を使っているチームにとって最も重要な点を見落とす。Opus 4.7 は同じ入力テキストに対して最大 35% 多くのトークンを生成する新しいトークナイザーを搭載している。そのため、レートカードが変わらなくても、実際の請求額は上昇する可能性がある。

移行前に必ずやること：

```python
# トークン数の差分を事前に計測する
import anthropic

client = anthropic.Anthropic()

sample_prompt = "（本番で使う典型的なプロンプトをここに）"

# Opus 4.6 のトークン数
count_46 = client.messages.count_tokens(
    model="claude-opus-4-6",
    messages=[{"role": "user", "content": sample_prompt}],
)

# Opus 4.7 のトークン数
count_47 = client.messages.count_tokens(
    model="claude-opus-4-7",
    messages=[{"role": "user", "content": sample_prompt}],
)

print(f"Opus 4.6: {count_46.input_tokens} tokens")
print(f"Opus 4.7: {count_47.input_tokens} tokens")
print(f"増加率: {count_47.input_tokens / count_46.input_tokens:.2f}x")
```

## プロンプトの書き直し：「暗黙の意図」はもう通じない

Opus 4.7 はより字義通りに指示に従うようになっており、あるアイテムへの指示を他へ無言で汎化したり、明示されていないリクエストを推論したりしなくなった。

4.6 向けのプロンプトが 4.7 で悪い結果を出す原因は、ほぼ例外なく「4.6 が暗黙のコンテキストを補完してくれていたが 4.7 はそれをしない」ことにある。明示的な intent・success criteria・constraints を書いてプロンプトを書き直すことが対応策になる。

## まとめ：移行チェックリスト

| # | 対応内容 | 優先度 |
|---|----------|--------|
| 1 | `claude-opus-4-6` → `claude-opus-4-7` に文字列置換 | 🔴 必須 |
| 2 | `temperature` / `top_p` / `top_k` を API コールから削除 | 🔴 必須 |
| 3 | `budget_tokens` を `thinking: {type: "adaptive"}` + `effort` に置換 | 🔴 必須 |
| 4 | thinking を UI に表示する場合は `display: "summarized"` を明示 | 🟠 推奨 |
| 5 | エージェントループに `task_budget` を設定 | 🟡 任意 |
| 6 | 本番プロンプトで事前にトークン数の差分を計測 | 🟠 推奨 |
| 7 | `max_tokens` に 20% 程度の余裕を追加 | 🟠 推奨 |

既存の Opus 4.6 ユーザーは急いで移行しないことを勧める。トークナイザーの影響をベンチマークし、字義通りの解釈による変化に対してプロンプトを再テストし、100% 移行前に本番トラフィックで検証しよう。モデルは改善されているが、移行はゼロコストではない。

モデルとしての実力は確かに上がっている。だが「価格据え置き＝そのまま動く」という期待で突っ込むと痛い目を見る。このチェックリストを一通り流してから本番のモデル名を切り替えてほしい。
